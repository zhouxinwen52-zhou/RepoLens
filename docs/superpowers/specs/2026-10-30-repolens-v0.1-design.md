# RepoLens V0.1 Design Specification

**Date:** 2026-10-30  
**Status:** Approved technical design  
**Product:** RepoLens  

## 1. Intent and Motivation

RepoLens is an opinionated Codex plugin for systematically understanding unfamiliar GitHub repositories and evaluating project ideas inspired by them.

The project starts from a real workflow: a junior software engineer discovers an interesting repository, wants to understand its architecture and most valuable concepts without reading every file, and may develop ideas worth exploring. Generic AI summaries are often inconsistent, overly broad, or insufficiently grounded in source code. RepoLens turns this learning and decision process into a repeatable, evidence-backed workflow.

RepoLens has two equally important outcomes:

1. **Product outcome:** a plugin that users can install and use regularly to learn from or adopt unfamiliar repositories and evaluate ideas.
2. **Learning outcome:** a real project through which the author learns requirements analysis, specification writing, Codex plugin composition, skill design, personalization, structured outputs, external skill integration, evals, and iterative delivery.

RepoLens is born from one person's workflow but is not hard-coded for one person. Its methodology is reusable; each user supplies a local Profile that changes the explanation depth, learning priorities, exercises, and idea evaluation.

## 2. Goals, Non-goals, and Anti-goals

### 2.1 Goals

- Turn repository study into a repeatable, profile-aware workflow.
- Route a repository to `LEARN`, `USE`, `BOTH`, or `SKIP` before doing expensive analysis.
- Explain architecture and one primary runtime flow using real source evidence.
- Generate validated architecture and runtime-flow diagrams through Archify.
- Help users distinguish what they know, what is worth learning, and what they can skip.
- Convert learning into one small applied exercise and a few traceable inspired ideas.
- Evaluate ideas with a stable rubric and recommend `BUILD`, `PROTOTYPE`, `SAVE`, or `SKIP`.
- Follow the current official OpenAI plugin packaging and skill conventions.
- Provide regression coverage based on structural invariants and fixture repositories.

### 2.2 Non-goals for V0.1

- Discovering or ranking GitHub Trending repositories. The existing `learn-from-github` project handles discovery; RepoLens begins with a repository selected by the user.
- Building or hosting a custom GitHub MCP server.
- Managing GitHub OAuth, tokens, or other credentials.
- Automatically installing third-party projects or running their code.
- Automatically executing the generated Applied Practice.
- Building a web dashboard, cloud account system, database, team collaboration, or profile sync.
- Supporting every language, framework, monorepo shape, or repository size.
- Building a compiler-grade dependency graph.
- Automatically creating projects recommended by `/evaluate-idea`.
- Publishing to the public plugin directory as part of V0.1 acceptance.

### 2.3 Anti-goals

- A generic repository summarizer that restates the README.
- A tool that explains every file with equal weight.
- A technology showcase that adds MCP, hooks, or UI without a demonstrated requirement.
- A confident-sounding analyzer that invents architecture or runtime steps without evidence.
- A fixed personal assistant whose assumptions cannot be changed by another user's Profile.

### 2.4 Supported execution and repository scope

The formal V0.1 acceptance environment is **Codex desktop on macOS**. Codex CLI compatibility is desirable and should be preserved when it does not complicate the primary design, but CLI support is not a V0.1 acceptance requirement. Other operating systems are best effort until separately tested.

V0.1 fixtures and explicit compatibility claims cover repositories whose primary implementation is **TypeScript, Python, or Java**. Other languages and mixed-language repositories may be analyzed on a best-effort basis, but RepoLens must disclose that status near the beginning of the result and must not claim complete entry-point or runtime-flow coverage.

## 3. Approaches Considered

### 3.1 Repository access

**Approach A: GitHub-first through a mandatory MCP server.** This would provide structured remote access and authentication, but would make the core workflow depend on one provider, complicate installation, and perform poorly for broad local source search.

**Approach B: local-only analysis.** This is reliable for deep source inspection but creates unnecessary friction for users who start with a GitHub URL and provides no graceful path for metadata, issues, releases, or private repositories.

**Chosen approach: local-first with optional acquisition adapters.** Existing local repositories are read directly. A GitHub URL can be shallow-cloned with Git; existing GitHub MCP/plugin or `gh` CLI capabilities may provide metadata, remote content, or authenticated access. RepoLens does not own credentials or a GitHub server. This keeps deep analysis reliable while allowing useful integrations.

### 3.2 Plugin shape

**Approach A: custom MCP-backed application.** This would provide controlled tools and potentially a UI, but no V0.1 requirement needs infrastructure operated by RepoLens.

**Approach B: one monolithic skill.** This minimizes files but mixes onboarding, repository learning, usage guidance, and idea evaluation into one difficult-to-test instruction set.

**Chosen approach: a skills-led plugin with three focused skills.** `setup-profile`, `learn-project`, and `evaluate-idea` remain separate user goals, with detailed rules in adjacent references and templates. Existing external tools are consumed when available; no custom MCP or hooks are bundled.

### 3.3 Visualization

**Approach A: hand-authored Mermaid or custom HTML/SVG.** This reduces external dependencies but duplicates layout, validation, interaction, and export behavior.

**Approach B: optional diagram decoration.** Text analysis would always count as complete, but visualization would become inconsistent and easy to omit.

**Chosen approach: Archify as a required companion for complete Learning Workflow output.** RepoLens owns evidence-backed analysis models and adapters; Archify owns its schema, validation, layout, and HTML artifact. Without Archify, RepoLens may return a degraded text/model result but must not mark the complete Learning Workflow successful.

### 3.4 Personalization

**Approach A: infer the user from conversation each run.** This requires repeated questions and makes outcomes unstable.

**Approach B: hard-code the original author's background.** This serves one person but prevents reuse.

**Chosen approach: a local, editable Markdown Profile with YAML frontmatter.** It is created during onboarding, remains human-readable, supplies structured fields for deterministic checks, and can be replaced by any user.

## 4. Target User and Core Experience

The primary V0.1 user is a software engineer who wants to learn from real open-source projects but lacks a consistent method for navigating unfamiliar repositories. The initial design is calibrated for a junior engineer, while Profile fields allow more experienced users to change depth and priorities.

Typical entry points are:

```text
Selected local repository or GitHub URL
→ learn-project

Independent idea or inspired idea
→ evaluate-idea
```

Repository discovery stays outside RepoLens. A user may copy a URL from `learn-from-github`, GitHub, an article, or work, then give it to RepoLens.

## 5. Profile and Onboarding

### 5.1 Profile Gate

Both primary workflows require a valid Profile. On first use:

```text
Install RepoLens
→ run setup-profile onboarding
→ answer a short set of questions
→ review generated Profile
→ confirm and save locally
→ resume the original task
```

If the Profile is missing, the requested workflow pauses and onboarding runs. If the Profile is invalid, RepoLens reports the exact field problem and helps repair it. It never silently creates a default persona.

The preferred host behavior is to resume the original request automatically in the same conversation with its repository or idea input preserved. If the host cannot resume automatically after onboarding, RepoLens returns one explicit continuation action containing enough context to restart the paused workflow without requiring the user to re-enter the original input.

### 5.2 Profile format

The Profile is Markdown with YAML frontmatter. V0.1 fields are:

- schema version;
- experience level;
- known languages, frameworks, and concepts;
- current learning goals;
- technical interests;
- career and portfolio goals;
- available weekly time;
- preferred explanation language and depth;
- Technical English preference;
- optional free-text context.

It does not contain tokens, API keys, passwords, or unnecessary identity data. It is stored in the plugin runtime's user-local writable data area, not in the installed plugin package and not in the repository being analyzed.

A per-run user instruction may temporarily override the Profile. Temporary overrides are not written back unless the user explicitly confirms the update.

### 5.3 Environment check

Onboarding reports:

```text
Local filesystem access: Available / Unavailable
git: Available / Missing
gh CLI: Available / Missing
GitHub MCP/plugin: Connected / Not connected
Archify: Available / Missing
```

Only local filesystem access is required for an already-local repository. Git is required for URL-based deep analysis. `gh` and GitHub MCP/plugin are optional. Archify is required for complete diagram output.

## 6. Repository Acquisition and Safety Boundary

RepoLens accepts the current workspace, a local path, or a GitHub repository URL.

For a local repository, it reads the checkout directly. For a URL, it validates and normalizes the GitHub URL, rejects embedded credentials, and uses a shallow Git clone when full source is needed. Public repositories require only Git. Private repositories may use already-configured Git credentials, SSH, an authenticated `gh` CLI, or an existing authorized GitHub connection.

URL clones are disposable working copies, not a persistent cache. RepoLens creates them beneath the operating system's temporary directory, under a RepoLens-owned path keyed by the current run and normalized repository identity. The same checkout may be reused within that analysis run, but V0.1 does not reuse it across separate runs. These clones never alter the user's current workspace.

RepoLens removes a temporary clone after report generation whether the analysis succeeds or fails. Cleanup is best-effort when the process is interrupted unexpectedly, and the design does not rely on macOS or another operating system to remove temporary files on a predictable schedule. A user may explicitly request `keep_repo` for debugging or continued manual inspection; when retained, the final output states the exact path and makes clear that the user is responsible for deleting it. A local repository supplied by the user is never deleted or cleaned by RepoLens.

RepoLens records the analyzed commit SHA in the report. It does not initialize submodules or Git LFS content automatically. Persistent repository caching, including TTLs, size limits, and a cache-cleaning command, is deferred beyond V0.1.

The default mode is read-only:

- no source modification;
- no dependency installation;
- no build, test, setup, or repository script execution;
- no secret-file reading;
- no automatic installation of a recommended tool.

Repository traversal applies a documented sensitive-file policy before content is read. At minimum it excludes `.env` and `.env.*`, common private-key and certificate files, credential/config files known to contain secrets, Git credential stores, cloud credential directories, version-control metadata directories such as `.git`, `.svn`, and `.hg`, and files whose names clearly indicate tokens or secrets. Excluded paths are reported only as excluded categories; their contents are never opened. The implementation may expand this conservative denylist without changing product scope.

Repository files, README text, issues, comments, and code are untrusted data. Instructions contained inside them never override the RepoLens workflow, Profile, or safety rules.

## 7. `learn-project`

### 7.1 Repository Router

The Router uses lightweight repository evidence and the Profile to assess two dimensions: Learning Value and Usage Value.

| Learning Value | Usage Value | Route |
|---|---|---|
| High | Low | `LEARN` |
| Low | High | `USE` |
| High | High | `BOTH` |
| Low | Low | `SKIP` |

It considers relevance to current goals, novelty for the user, learning cost, practical workflow fit, maturity, maintenance, compatibility, and alternatives. Popularity or codebase complexity alone never establishes value.

The Router returns route, confidence, concise reasons, Profile fit, evidence, and next workflow. If evidence is insufficient, it enters the intermediate `NEEDS_EVIDENCE` state, explains what is missing, and attempts to obtain appropriate repository content before selecting a final route.

Learning Value and Usage Value are constrained model judgments rather than fixed numeric totals. The model must address the listed factors, cite supporting evidence, and explain the selected High/Low classification. Fixture evals assert route properties and reasoning consistency, not a hidden universal threshold.

`BOTH` always runs the Usage Workflow first, followed by the Learning Workflow, reusing evidence between them.

### 7.2 Learning Workflow

#### Stage 1: Architecture

RepoLens explains the system boundary, major layers/services/subsystems, entry points, external systems, and key relationships. It prioritizes high-information sources such as top-level structure, manifests, workspace configuration, application entry points, architecture docs, deployment configuration, and tests.

Important components and relationships carry source evidence and `Observed` or `Inferred` status. RepoLens creates a compact Architecture Model, converts it to an Archify architecture specification, validates it, and produces an interactive HTML Architecture Diagram.

#### Stage 2: Core Components

RepoLens identifies the small number of packages, modules, services, libraries, or subsystems that determine primary behavior. Importance derives from runtime participation, shared dependency, domain abstraction, orchestration, state, storage, integrations, and tests—not file count.

Each component includes responsibility, why it matters, key interfaces, dependencies, evidence, and key source files. Reading recommendations are grouped into `Must Read`, `Worth Reading`, and `Reference Only`.

#### Stage 3: Main Runtime Flow

RepoLens selects one primary end-to-end flow that best represents the project's value. It starts at a real trigger or entry point and follows the happy path through important components to an observable result.

Each step records participant, file, symbol, input, action, output, next step, and evidence. The trace includes important data/state changes, asynchronous boundaries, external interactions, and only the failure branches that materially change the main flow. Dynamic dispatch or framework magic is identified explicitly; missing links stop the trace rather than being invented.

RepoLens converts the Runtime Flow Model into an Archify `sequence`, `workflow`, or `dataflow` specification according to the flow's shape, validates it, and produces an interactive HTML Runtime Flow Diagram.

#### Stage 4: Technical Concepts

RepoLens selects only the few concepts needed to understand the confirmed architecture or runtime flow. Each concept contains:

```text
Concept Name
Plain-language Explanation
How This Repo Uses It
```

It does not produce a generic technology list or an independent tutorial.

#### Stage 5: Technical English

RepoLens extracts a target of 10-15 reusable engineering expressions from real README, documentation, configuration, error messages, or comments. Each contains:

```text
Technical Expression
Meaning in Context
How Engineers Use It
```

Quality takes priority over quota; fewer items are acceptable when the source does not contain enough high-value expressions. Long excerpts and ordinary vocabulary are excluded.

If the Profile disables Technical English practice, Stage 5 remains present as `Skipped by Profile`. This is an intentional personalization choice and does not make the Learning Workflow incomplete.

#### Stage 6: Known / New / Can Skip

Using the Profile, RepoLens classifies only learning-relevant components, concepts, mechanisms, and practices:

- `Known`: already mastered; mention only repository-specific twists.
- `New`: relevant and worth learning; include a concrete place to start.
- `Can Skip`: currently low ROI, unrelated, or implementation detail; explain why skipping is reasonable now.

If the Profile cannot support a classification, RepoLens marks it `Unclear` as an information state and asks only when the answer affects the workflow.

#### Stage 7: Applied Practice

RepoLens produces one small practice brief centered on one high-value New concept. It contains title, concept, why it fits, task, constraints, success criteria, time estimate based on the Profile, and one to three hints. It must be independently achievable without copying the whole repository or requiring unrelated infrastructure. RepoLens does not create or implement the practice automatically.

If the Profile and repository evidence contain no defensible high-value `New` concept, RepoLens does not invent one or revise an otherwise valid `LEARN` route. It instead creates a repository-specific exercise around a relevant `Known` concept and labels the practice `Reinforcement`.

#### Stage 8: Inspired Ideas

RepoLens preserves user ideas and may generate one to three AI-inspired ideas grounded in a specific repository mechanism, limitation, or workflow. User ideas and AI ideas are labeled separately. Each idea includes inspiration, short description, preliminary Profile fit, unknowns, and possible handoff to `evaluate-idea`. No forced ideas are generated when none are valuable.

V0.1 preserves ideas only in the current Learning Report and the immediate handoff to `evaluate-idea`. It does not maintain a persistent cross-run idea library.

The completed Learning Report is saved as a durable local Markdown artifact in RepoLens's user-local writable data area. Validated Archify Architecture and Runtime Flow diagrams are saved as local HTML artifacts and linked from the report. Artifact-save failure preserves the conversation result, marks artifact delivery incomplete, and reports recovery guidance. RepoLens never writes reports into a user-provided repository unless the user explicitly requests that destination.

### 7.3 Usage Workflow

The Usage Workflow remains intentionally small:

1. **What It Does & Personal Fit:** the problem, core capability, workflow fit, and overlap with current tools.
2. **Requirements & Risks:** only prerequisites, permissions, cost, compatibility, maintenance, and safety concerns that affect adoption.
3. **Quick Start:** official installation, minimal configuration, first useful task, expected result, and verification. RepoLens provides guidance only.
4. **Recommendation:** `USE NOW`, `SAVE FOR LATER`, or `SKIP`, with one-sentence reasoning, smallest next step, and largest risk.

### 7.4 Progress and timing

Long-running repository work reports the current workflow and stage through the host conversation. Each major stage records start and completion timestamps in run metadata so fixture and manual-acceptance runs can establish duration baselines. V0.1 has no fixed universal time SLA and does not present an estimated completion time it cannot support.

## 8. `evaluate-idea`

### 8.1 Workflow

```text
Idea
→ Clarify
→ Check Existing Solutions
→ Apply Rubric
→ Decide & Scope
```

Clarification produces Problem, Target User, Proposed Solution, Why Now, and Source. Existing-solutions research identifies comparable products/projects, their current coverage, meaningful differences, and unknowns. If reliable external research is unavailable, RepoLens marks affected claims and scores `Unknown` rather than fabricating market knowledge.

Before any idea details are sent to an external research or search capability, RepoLens discloses the external lookup and obtains explicit consent for that evaluation. If consent is declined, RepoLens continues locally and marks affected Existing Solutions or Novelty evidence `Unknown`.

Problem, Target User, and Proposed Solution must be clear enough to evaluate. If they are not, RepoLens returns an incomplete clarification result rather than forcing rubric scores or a final decision.

### 8.2 Rubric

All numeric dimensions use 1-5, where higher means more support for investment. Scores 2 and 4 fall between anchors.

| Dimension | 1 | 3 | 5 |
|---|---|---|---|
| Novelty | No meaningful difference | Partial differentiation | Clear, important differentiation |
| Learning ROI | Familiar or cost outweighs learning | Some useful learning | Concentrated practice of current high-value skills |
| Portfolio Value | Hard to demonstrate or explain | Shows some capability | Strong, coherent engineering story |
| Goal Alignment | Unrelated or conflicting | Some relevance | Directly serves current goals |
| Feasibility | Not achievable with current resources | Achievable after scoping | Independently achievable and verifiable in reasonable time |
| Skill Fit | Too familiar or far beyond current ability | Challenging with substantial support | Appropriate stretch with useful foundations |

Each dimension includes Reason, Evidence, and Confidence (`High`, `Medium`, or `Low`). Evidence and confidence are not averaged into the value score. Missing information produces `Unknown` plus a concrete verification need.

### 8.3 Decisions

- `BUILD`: high alignment, worthwhile learning or portfolio value, sufficient feasibility, and a clear initial scope.
- `PROTOTYPE`: promising but dependent on one or more quickly testable assumptions.
- `SAVE`: potentially valuable, but current timing, goals, or capacity do not fit; include a reevaluation condition.
- `SKIP`: expected value remains too low even after reasonable scoping.

The decision is not a simple average. It must be explained through the rubric, identify the largest unknown, and include the smallest useful scope and next action. RepoLens does not create the project automatically.

RepoLens does not issue `BUILD` while a critical dimension remains `Unknown`. A cheaply testable critical unknown normally leads to `PROTOTYPE`; missing evidence, timing, or capacity may lead to `SAVE` with a reevaluation condition; sufficient negative evidence may still justify `SKIP` despite non-critical unknowns.

Criticality is contextual rather than a fixed dimension list. RepoLens must name each critical unknown, explain why it could change the current decision, and state how to verify it. `BUILD` requires Goal Alignment and Feasibility to be known and no other decision-changing unknown to remain.

Idea Evaluations are returned as structured conversation output by default. RepoLens saves a durable local Markdown copy only when the user explicitly requests it; V0.1 does not maintain an automatic cross-run idea or evaluation database.

## 9. Archify Integration and Analysis Models

RepoLens owns truth extraction; Archify owns visualization.

The Architecture Model contains repository identity/ref, components, external systems, entry points, relationships, evidence references, and confidence. The Runtime Flow Model contains flow name, trigger, participants, ordered steps, data/state changes, critical branches, final result, evidence references, and confidence.

Evidence references contain file path, optional symbol or document section, observation, status (`Observed` or `Inferred`), and confidence. Diagram nodes need not display all evidence, but every important diagram element must be traceable through the accompanying report.

For each diagram, RepoLens creates a fresh Archify typed specification, runs Archify validation, and delivers the HTML only after validation succeeds. A validation failure preserves the analysis model, reports the error, and never presents a stale or failed artifact as successful.

Archify availability is checked during onboarding. Without it, RepoLens may return text and analysis models in degraded mode, but the complete Learning Workflow acceptance condition is not met.

### 9.1 Artifact delivery

RepoLens stores generated artifacts beneath the host-provided user-local plugin data directory, outside both the installed plugin package and the analyzed repository. Each Learning run receives a sanitized repository identity plus unique run directory containing:

```text
report.md
architecture.html      # only after successful Archify validation
runtime-flow.html      # only after successful Archify validation
```

The report links to the diagram files with relative paths so the run directory remains movable. Files are written through temporary sibling files and renamed only after successful completion, preventing a partially written artifact from appearing complete. A failed write preserves the conversation result and returns the intended destination plus recovery guidance.

Idea Evaluations use no automatic artifact directory. When a user explicitly requests saving one, RepoLens writes a Markdown file under the same user-local data area and returns its path. No index, database, telemetry event, or cross-run idea collection is created.

## 10. Plugin Structure

V0.1 uses the current portable plugin layout as the primary format:

```text
RepoLens/
├── plugin.json
├── README.md
├── LICENSE
├── skills/
│   ├── setup-profile/
│   │   ├── SKILL.md
│   │   ├── agents/openai.yaml
│   │   ├── references/profile-schema.md
│   │   └── assets/profile-template.md
│   ├── learn-project/
│   │   ├── SKILL.md
│   │   ├── agents/openai.yaml
│   │   ├── references/
│   │   └── assets/learning-report-template.md
│   └── evaluate-idea/
│       ├── SKILL.md
│       ├── agents/openai.yaml
│       ├── references/evaluation-rubric.md
│       └── assets/idea-evaluation-template.md
├── assets/
├── evals/
└── tests/
```

The root `plugin.json` contains portable identity and OpenAI-specific presentation/onboarding metadata. `setup-profile` is declared as the onboarding skill. A `.codex-plugin/plugin.json` compatibility overlay is added only if verified local compatibility requires it; the root manifest remains canonical.

No `mcp.json`, hooks, custom UI, or custom server is created for V0.1. Stable external MCP dependencies may be declared per skill only after their actual identifiers and availability are verified. Archify companion detection is handled through onboarding because the current verified design does not assume a generic cross-plugin skill dependency field.

The installed plugin emits no analytics or telemetry and sends no Profile or report data to a RepoLens-operated service. External idea research is the only product flow that may send an idea description to a search capability, and it is guarded by the per-evaluation consent rule in Section 8.

RepoLens may include small, source-controlled helper scripts for deterministic work such as Profile/schema validation, URL normalization, temporary-clone lifecycle management, evidence/model validation, and test harness orchestration. Scripts must remain inspectable, narrowly scoped, and invoked by documented skill steps. V0.1 does not bundle opaque native binaries or move workflow judgment into an unreviewable executable.

V0.1 implements these deterministic helpers in TypeScript on Node.js. The plugin itself remains primarily Markdown, JSON, and YAML; TypeScript is an implementation aid rather than the product's workflow engine. Python remains one of the explicitly tested target-repository languages, not a second RepoLens runtime.

The conceptual product names `/learn-project` and `/evaluate-idea` remain in the design. README instructions use the actual invocation syntax supported by the target Codex client, such as direct skill invocation, after implementation-time verification.

## 11. Reliability and Error Handling

- Missing Profile: pause, run onboarding, then resume the original task.
- Invalid URL/path: identify the validation, access, or repository problem before analysis.
- Private access denied: direct the user to existing Git/`gh`/GitHub authorization; never request pasted tokens.
- Insufficient evidence: return `NEEDS_EVIDENCE`, missing data, attempted sources, and recovery action.
- Large repository: inspect structure, manifests/docs, entry points, selected components, and one primary flow in stages; report analyzed scope.
- Documentation/source conflict: report both claims and confidence instead of hiding the discrepancy.
- Archify unavailable: degraded text/model output, incomplete status.
- Archify validation failure: no diagram delivery, preserve typed input and diagnostics.
- External research unavailable: `Unknown` where required; lower confidence.
- External idea research declined: continue locally and mark affected Existing Solutions or Novelty evidence `Unknown`.
- Artifact save failure: preserve the conversation result, mark artifact delivery incomplete, and return the intended destination plus recovery guidance.
- Partial completion: list completed stages, incomplete stages, reason, and recovery.

Evidence is generally prioritized as source/configuration, tests, maintained technical docs, README, metadata, and inference, while recognizing that any source may be stale. Conflicts are reported explicitly.

## 12. Testing and Evaluation

### 12.1 Two separate execution paths

Normal RepoLens usage and developer model evaluation are intentionally separate:

```text
Normal user in Codex
→ invokes RepoLens skills
→ uses the user's existing Codex/ChatGPT product allowance
→ does not provide an OpenAI API key to RepoLens

RepoLens developer running model evals
→ sets OPENAI_API_KEY in the development environment
→ runs a low-cost API model against the five local fixture repositories
→ validates outputs against expected semantic properties
→ pays the resulting API usage separately
```

The installed plugin does not request, read, store, or transmit an OpenAI API key. The Profile and plugin manifest never contain one. `OPENAI_API_KEY` is consumed only by the developer-only eval runner and is never written to disk or included in test output.

`npm test` runs deterministic tests without a key or network access. `npm run eval:model` is the explicit paid model-evaluation command; it requires `OPENAI_API_KEY`, uses a configurable low-cost model selected at implementation time, and analyzes only RepoLens-owned fixture repositories. TypeScript checks the resulting structured outputs against expected properties. V0.1 does not add a second model grader or a complex multi-model evaluation system.

The API eval validates the RepoLens methodology and structured output. Codex plugin installation, host skill invocation, and Archify rendering remain part of the separate Codex desktop manual acceptance check.

### 12.2 Test layers

1. **Plugin structure tests:** manifest/schema validity, paths, skill metadata, Profile schema, resource links, and local marketplace recognition.
2. **Deterministic contract tests:** allowed Router/decision enums, required workflow stages, analysis-model schemas, valid evidence references, and valid Archify adapter output.
3. **Repository model eval harness:** five small, fixed fixture repositories covering a conventional web service, RAG application, MCP server, agent project, and unfamiliar architecture. A low-cost API model analyzes each fixture and TypeScript validates the output against its expected-properties manifest.
4. **Idea evaluation fixtures:** ideas paired with multiple Profiles and expected decision properties.
5. **Artifact and consent tests:** durable report/diagram writing, repository-write protection, save-failure recovery, Technical English opt-out, Reinforcement fallback, external-research consent/decline, and critical-unknown decision boundaries.

Fixtures are local or pinned to immutable commits. Each has an expected-properties manifest containing architecture, entry points, core components, runtime-flow edges, high-value files, forbidden claims, important concepts, and acceptable variations. Tests never require identical prose.

### 12.3 Invariants

- Architecture and runtime flow are factually grounded.
- Key flow nodes map to real files or symbols.
- Forbidden or unsupported claims do not appear.
- Recommended source files are genuinely high value.
- Profile changes personalization but not repository facts.
- Repeated runs preserve core conclusions within reasonable variation.
- Rubric reasons and final decisions remain consistent.
- Missing evidence produces uncertainty rather than invented facts.
- Failed Archify validation never counts as successful delivery.
- A Profile-disabled Technical English stage remains complete and visibly skipped.
- Applied Practice never invents a `New` concept when only `Known` concepts are supported.
- Idea content is not sent to external research without recorded consent.
- `BUILD` never appears when Goal Alignment, Feasibility, or another decision-changing fact is unknown.
- Durable artifacts remain outside the analyzed repository unless the user explicitly chooses that destination.

Human review checks factual grounding, learning usefulness, concision, traceability, material personalization, and whether the recommended action makes sense.

## 13. V0.1 Acceptance Criteria

V0.1 is complete when a user can:

1. Install RepoLens through a supported local plugin flow.
2. Complete first-use onboarding and save a valid local Profile.
3. Submit a local repository, path, or GitHub URL.
4. Receive an evidence-backed `LEARN`, `USE`, `BOTH`, or `SKIP` route.
5. Complete the selected deterministic workflow.
6. For Learning, receive validated Architecture and Runtime Flow diagrams plus the eight learning stages.
7. Send an independent or inspired idea through the six-dimension rubric and receive a justified `BUILD`, `PROTOTYPE`, `SAVE`, or `SKIP` decision.
8. Pass representative fixture evals without critical factual, evidence, safety, or workflow regressions.
9. Reopen a saved Learning Report and its validated diagram HTML files after the originating conversation.
10. Decline external idea research and still receive a local evaluation with the affected evidence marked `Unknown`.

Development acceptance additionally requires the five-fixture `npm run eval:model` suite to pass with a developer-supplied API key. This does not make an API key a runtime requirement for plugin users.

The core acceptance statement is:

> After installing RepoLens and creating a Profile, a user can give it a selected unfamiliar repository, receive an evidence-backed, personalized, visual learning or usage path, and make a structured decision about ideas inspired by that repository.

## 14. Builder Decisions That Remain Implementation-local

The implementation plan may select exact filenames, validation libraries, temporary-directory naming mechanics, test runner, and fixture implementations as long as it preserves this specification. It must re-check current official OpenAI plugin schemas, invocation syntax, marketplace behavior, and external dependency mechanisms at implementation time because those platform contracts may evolve.

Any proposal to add a custom MCP server, hooks, automatic installation, repository discovery, or custom UI changes V0.1 scope and requires a design revision rather than an implementation shortcut.
